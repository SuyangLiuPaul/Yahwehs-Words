## `audit_note_placement.py` — the baseline's own summary mislabels its one finding

**Not new drift.** `assets/cuvs-yhwh-tr.json` has not changed since
`b6bd459c` (`git log b6bd459c..HEAD -- assets/cuvs-yhwh.json
assets/cuvs-yhwh-tr.json` is empty) — the asset this pass read is
byte-identical to what the baseline pass read a few hours earlier. So
this is the *same* finding, transcribed wrong.

Today's queue entry for the baseline pass says: *"`audit_note_placement.py`
— 1,025 printed notes, 110 checkable, 1 ATTACHED ELSEWHERE (那鴻書 3:4,
already known)."* That is two separate errors stacked:

1. 那鴻書 3:4 (`034003004`) is not, and structurally cannot be, an
   ATTACHED ELSEWHERE case. The script's own `wrong` list (ATTACHED
   ELSEWHERE) and `split` list (DIFFERENT OCCURRENCE) are disjoint; 那鴻書
   3:4 lives in the `UNSETTLED` dict, which only suppresses `split`. This
   run's own output confirms it isn't even reaching that check any more:
   our note for that verse now explicitly names the word inside itself
   (`"誘惑"原文是"賣"`), which trips the script's earlier
   "note names the word itself, so it can't be misread" shortcut
   (`audit_note_placement.py:191-194`) before the occurrence check ever
   runs — hence `DIFFERENT OCCURRENCE 0` this run, not 1, and `12`
   verses with a repeated named word this run, not the docstring's `18`.
   (Not fixed this hour — `UNSETTLED["034003004"]` is now argument
   about dead code, but the reasoning it records is still true content
   about the verse and I did not touch it.)
2. The actual ATTACHED ELSEWHERE case is **`004001050`** (民數記 1:50,
   Numbers), never filed anywhere in the queue under any name.

**民數記 1:50** — ours: `他們要抬帳幕和其中的器具<note:
"擡"或作："搬運">，並要辦理帳幕的事` (note after 器具, the object, naming
擡). Print: `他們要抬{{*|抬或作搬運}}帳幕和其中的器具` (note right after
抬, the verb, naming 抬). The script's self-naming shortcut doesn't fire
here because our note names 擡 (an alternate character, not simplified by
`opencc t2s`) while the print's named word is 抬 — different characters,
so the string-containment check fails even though they are the same word.
A human reader is not actually misled (the note names its own referent
either way), but the script's stricter test is right to flag it: this is
the one place in 110 checkable notes where our copy both moved the note
AND changed which character it names, and nobody has read it against the
print before. **Asset is frozen (`assets/cuvs-yhwh-tr.json`), so this
cannot be repaired even if it turned out to want one — filing only.**

Filed as a new queue item below; the mislabeled `b6bd459c` entry is left
as-is (an `[x]` item, already closed) with this file linked from the new
entry per the "don't rewrite closed history, add a correcting entry"
convention this queue already uses.
